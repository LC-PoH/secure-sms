ABSTRACT
============================================================

This report documents the design, implementation, and security evaluation
of SecureSMS — a secure web-based Student Management System built using
Python (Flask) and the Secure Software Development Lifecycle (SSDLC)
framework. The system enables administrators, teachers, and students to
manage academic records through a role-based interface, with all personally
identifiable information (PII) protected by AES-256-GCM field-level
encryption. Advanced security features include Time-based One-Time Password
(TOTP) two-factor authentication (2FA), bcrypt password hashing, CSRF
protection, SQL injection prevention via ORM, XSS input sanitisation, and
JWT-secured REST API endpoints. All seven SSDLC phases — from Security
Requirements through Maintenance and Monitoring — are documented, and the
system successfully mitigates the OWASP Top 10 vulnerability categories
relevant to web applications. The working prototype demonstrates that
security-first design principles can be integrated into every phase of
development without compromising usability.

Key outcomes: functional web application with 12 active security controls,
zero OWASP Top 10 vulnerabilities in the implemented scope, complete audit
trail, and a JWT REST API for system integration.

1. INTRODUCTION
============================================================

1.1 Problem Statement

Student management systems routinely process sensitive PII — names, email
addresses, phone numbers, grades, and enrolment data. When these systems
lack security controls, they become high-value targets for data breaches,
identity theft, and academic fraud. A 2023 Verizon Data Breach
Investigations Report found that 74% of breaches involved the human element,
including credential abuse and social engineering, and that educational
institutions faced a disproportionate volume of denial-of-service and
web-application attacks (Verizon, 2023).

Traditional student management systems (e.g., those built with basic
username/password authentication and no encryption at rest) are vulnerable
to: SQL injection attacks against student databases; brute-force credential
attacks against poorly protected login pages; insider-threat grade
manipulation with no audit trail; and session hijacking through insecure
cookie handling.

1.2 Security Context

The General Data Protection Regulation (GDPR) and New Zealand's Privacy Act
2020 require organisations to implement appropriate technical measures to
protect personal data. For a student management system, this mandates
encryption at rest, access controls, breach notification procedures, and
data minimisation. SecureSMS is designed to satisfy these requirements within
an educational prototype context.

1.3 Project Objectives

The objectives of this project are to:
(a) Apply all seven phases of the Secure Software Development Lifecycle to
    the design and implementation of a student management system;
(b) Implement advanced security features including AES-256-GCM encryption,
    TOTP 2FA, bcrypt hashing, RBAC, and JWT API authentication;
(c) Prevent OWASP Top 10 vulnerabilities through secure coding practices;
(d) Demonstrate that security controls are functional through a working
    prototype;
(e) Provide a complete audit trail of all security-relevant events.

2. LITERATURE REVIEW
============================================================

2.1 OWASP Top 10 and Web Application Security

The Open Web Application Security Project (OWASP) Top 10 is the most widely
referenced framework for web application security risks. The 2021 edition
identifies Broken Access Control as the top risk, followed by Cryptographic
Failures, Injection, and Insecure Design (OWASP, 2021). Each of these
categories is directly relevant to student management systems, which must
protect PII across multiple user roles and interface with databases that
store sensitive academic records.

SQL Injection (OWASP A03:2021) remains one of the most exploited
vulnerabilities in web applications. According to Clarke (2012), SQL
injection enables attackers to bypass authentication, extract entire database
contents, and modify or destroy data. Parameterised queries and
Object-Relational Mappers (ORMs) are the most effective preventive controls.

2.2 Authentication Security

Multi-factor authentication (MFA) is consistently identified as one of the
highest-impact security controls available. The US National Institute of
Standards and Technology (NIST) SP 800-63B guidelines recommend that
authentication systems implement phishing-resistant MFA and mandate that
memorised secrets (passwords) meet complexity and length requirements of at
least 8 characters, with higher-security systems requiring 12 or more
(NIST, 2017). Time-based One-Time Passwords (TOTP), defined in RFC 6238
(Mraihi et al., 2011), provide a widely supported and computationally
lightweight second factor.

Bcrypt, designed by Provos and Mazières (1999), remains the recommended
algorithm for password hashing in web applications due to its configurable
work factor — meaning the computational cost can be increased over time as
hardware improves (OWASP, 2021b). Flask-Bcrypt implements this at work
factor 12, providing approximately 250 ms per hash computation, which
effectively prevents offline brute-force attacks.

2.3 Data Encryption at Rest

AES (Advanced Encryption Standard) in GCM (Galois/Counter Mode) is the
NIST-recommended symmetric encryption algorithm for protecting data at rest
(NIST FIPS 197, 2001). AES-256-GCM provides both confidentiality (256-bit
key) and integrity (authentication tag), meaning any tampered ciphertext
will be detected and rejected. GCM mode requires a unique 96-bit nonce per
encryption operation, which SecureSMS generates using a CSPRNG
(Cryptographically Secure Pseudo-Random Number Generator) via Python's
os.urandom().

2.4 Role-Based Access Control

Role-Based Access Control (RBAC), formalised by Sandhu et al. (1996), is the
dominant access control model in enterprise applications. RBAC assigns
permissions to roles rather than individual users, making authorisation
policies easier to manage and audit. SecureSMS implements three roles —
Admin, Teacher, and Student — with strictly enforced permission boundaries
at both the view and API layers.

2.5 SSDLC Frameworks

The Secure Software Development Lifecycle integrates security into every
phase of software development, from requirements through maintenance.
Microsoft's SDL (Security Development Lifecycle), OWASP's SAMM (Software
Assurance Maturity Model), and NIST's SP 800-64 all converge on the same
core principle: security activities conducted earlier in the lifecycle are
significantly less expensive to implement and more effective than those
applied post-deployment (McGraw, 2006). This project follows a seven-phase
SSDLC model adapted from the course materials.

3.2 Core Security Requirements

The following security requirements were defined before implementation began,
following the STRIDE threat model's CIA triad mapping:

Confidentiality Requirements:
  SR-C1: All PII fields (name, email, phone, grade) MUST be encrypted at rest
         using AES-256-GCM.
  SR-C2: Passwords MUST be stored as bcrypt hashes (work factor ≥ 12).
  SR-C3: Session tokens MUST be HttpOnly and SameSite=Lax cookies.
  SR-C4: Database credentials MUST NOT be hard-coded in source code.

Integrity Requirements:
  SR-I1: All form submissions MUST include a CSRF token.
  SR-I2: All user inputs MUST be sanitised against XSS before storage.
  SR-I3: AES-GCM authentication tags MUST be verified on every decryption.
  SR-I4: An immutable audit log MUST record every authentication and
         data-mutation event.

Availability Requirements:
  SR-A1: Login endpoints MUST enforce rate limiting (10/min per IP).
  SR-A2: Accounts MUST be locked for 15 minutes after 5 failed login
         attempts.
  SR-A3: Error pages MUST NOT expose stack traces or system information.

Authentication Requirements:
  SR-AU1: All users MUST complete TOTP 2FA setup on first login.
  SR-AU2: Passwords MUST be ≥ 12 characters with uppercase, lowercase,
          digit, and special character.
  SR-AU3: Sessions MUST expire after 30 minutes of inactivity.
  SR-AU4: Logout MUST invalidate the entire server-side session.

Authorisation Requirements:
  SR-AZ1: RBAC MUST be enforced at the route and API level for all roles.
  SR-AZ2: Teachers MUST only access students enrolled in their courses.
  SR-AZ3: Students MUST only access their own record.

4.1 System Architecture Overview

The SecureSMS architecture comprises four layers:

  [Browser / API Client]
        |  HTTPS (TLS)
        |
  [Flask Web Application — app/]
    ├── auth/          Authentication & 2FA
    ├── admin/         User and course management

    ├── student/       Self-service portal
    └── api/           JWT REST API
        |
  [SQLite / PostgreSQL Database]
    ├── user           (hashed passwords, TOTP secrets)
    ├── student        (AES-256-GCM encrypted PII)
    ├── course         (plaintext metadata)
    └── audit_log      (immutable event log)

Trust Boundaries:
  TB1: Browser — Flask application (HTTP, CSRF-protected)
  TB2: Flask application — Database (ORM, parameterised queries)
  TB3: API Client — Flask API (JWT Bearer token)

Entry Points:
  EP1: /auth/login — unauthenticated, rate-limited
  EP2: /auth/verify-2fa — pre-auth session state
  EP3: /teacher/students/* — authenticated + RBAC + 2FA
  EP4: /admin/* — admin role required + 2FA
  EP5: /api/v1/* — JWT Bearer token required

4.2 STRIDE Threat Analysis

S — Spoofing Identity
  Threat S1: Attacker submits forged credentials to impersonate admin.
  Risk: Critical (likelihood 4, impact 5) = 20
  Mitigation: bcrypt password hashing; account lockout after 5 failures;
              TOTP 2FA required; rate limiting (10 req/min).
  Status: MITIGATED

  Threat S2: Session token theft via XSS.
  Risk: High (likelihood 3, impact 4) = 12
  Mitigation: HttpOnly cookies (JS cannot access); CSP prevents script
              injection; bleach sanitises all inputs.
  Status: MITIGATED

T — Tampering
  Threat T1: SQL injection to modify student grades.
  Risk: Critical (likelihood 4, impact 5) = 20
  Mitigation: SQLAlchemy ORM — zero raw SQL queries anywhere in codebase.
              All queries use bound parameters.
  Status: MITIGATED

  Threat T2: CSRF attack forces grade update while teacher is logged in.
  Risk: High (likelihood 3, impact 4) = 12
  Mitigation: Flask-WTF CSRF token on all state-changing forms;
              SameSite=Lax cookies.
  Status: MITIGATED

  Threat T3: Encrypted PII tampered with in the database.
  Risk: Medium (likelihood 2, impact 4) = 8
  Mitigation: AES-GCM authentication tag — decryption fails and raises
              exception if ciphertext has been modified.
  Status: MITIGATED

R — Repudiation
  Threat R1: Admin denies creating or deleting a user account.
  Risk: Medium (likelihood 2, impact 3) = 6
  Mitigation: AuditLog table records every USER_CREATE, USER_DELETE event
              with timestamp and IP address.
  Status: MITIGATED

I — Information Disclosure
  Threat I1: Attacker reads database file and obtains student PII.
  Risk: Critical (likelihood 3, impact 5) = 15
  Mitigation: AES-256-GCM field encryption — all PII is ciphertext in DB.
              Encryption key stored in .encryption_key file (not in DB).
  Status: MITIGATED

  Threat I2: Error pages leak stack traces revealing system internals.
  Risk: Medium (likelihood 3, impact 3) = 9
  Mitigation: Custom 403/404/429/500 error handlers; debug=False in
              production; generic error messages in auth flows.
  Status: MITIGATED

D — Denial of Service
  Threat D1: Brute-force login attack floods the server.
  Risk: High (likelihood 4, impact 3) = 12
  Mitigation: Flask-Limiter: 10 requests/minute on /auth/login and
              /auth/verify-2fa; 5 requests/minute on /api/v1/token.
              Account lockout: 15 min after 5 failures.
  Status: MITIGATED

E — Elevation of Privilege
  Threat E1: Student directly accesses /admin/users URL.
  Risk: High (likelihood 3, impact 4) = 12
  Mitigation: @role_required('admin') decorator on every admin route;
              @require_2fa decorator — session must have '2fa_verified'.
              403 Forbidden returned with no detail.
  Status: MITIGATED

  Threat E2: Teacher accesses another teacher's students via API.
  Risk: Medium (likelihood 2, impact 4) = 8
  Mitigation: Object-level authorisation in API: teacher's JWT identity
              checked against course membership before returning student data.
              OWASP API1 — Broken Object Level Authorisation prevention.
  Status: MITIGATED

5. SECURE DESIGN (SSDLC PHASE 3)
============================================================

5.1 Principles Applied

Principle of Least Privilege:
  Each role can only access the minimum routes, data, and operations needed.
  Admin: full system. Teacher: their courses' students only. Student: own
  record only. Enforced through @role_required() decorator at every route
  and object-level checks within views.

Defence in Depth:
  Multiple security layers are applied independently, so that no single
  control failure leads to a breach:
    Layer 1: Rate limiting (prevents brute force reaching auth logic)
    Layer 2: bcrypt verification (prevents successful credential stuffing)
    Layer 3: TOTP 2FA (prevents login even with valid password)
    Layer 4: RBAC (prevents lateral movement post-authentication)
    Layer 5: AES-256-GCM (protects data even if DB is directly accessed)

Fail-Secure Design:
  All authentication and authorisation checks default to denial:
  - If 2FA flag not set in session → redirect to 2FA page
  - If role not in allowed list → HTTP 403
  - If AES decryption fails (tampered ciphertext) → exception raised
  - If CSRF token invalid → HTTP 400 (WTForms rejects form)

Minimal Attack Surface:
  No debug mode in production. No admin interfaces publicly exposed without
  authentication. No raw SQL. No user-controlled redirects. API endpoints
  are JWT-only and CSRF-exempt (stateless).

Separation of Duties:
  Admin manages users and courses but cannot directly modify grades (teacher
  role required). Audit log is append-only — no UI provides deletion.

5.2 Data Flow and Encryption Architecture

When a teacher saves a student record, the following encrypted data flow occurs:

  1. Form input received → bleach.clean() strips HTML/XSS
  2. WTForms validators check field format constraints
  3. sanitise_input() strips whitespace and control characters
  4. encrypt_field(plaintext, AES-256 key) → CSPRNG nonce + AES-GCM
  5. Base64URL-encoded ciphertext stored in database
  6. AuditLog entry written with user_id, action, timestamp, IP

On retrieval:
  1. SQLAlchemy ORM fetches ciphertext row (parameterised query)
  2. decrypt_field(ciphertext, key) → verifies GCM tag, returns plaintext
  3. Jinja2 auto-escaping applies HTML encoding on render (XSS layer 2)

6.2 Key Security Implementation Details

AES-256-GCM Field Encryption (app/utils/crypto.py):
  A 256-bit (32-byte) key is generated once on first run using os.urandom(32)
  and persisted to .encryption_key. Each encrypt_field() call generates a
  fresh 96-bit nonce via os.urandom(12). The ciphertext is stored as
  Base64URL(nonce || ciphertext || GCM_tag). This ensures that:
  - The same plaintext encrypts to different ciphertexts each time (nonce
    uniqueness)
  - Any tampering with the ciphertext is detected before decryption
  - The encryption key is never stored in the database

bcrypt Password Hashing (app/auth/routes.py):
  Passwords are hashed with work factor 12 using Flask-Bcrypt. The hash
  is stored in the user table. bcrypt.check_password_hash() performs
  constant-time comparison, preventing timing oracle attacks. Raw passwords
  are never logged, stored, or transmitted after verification.

TOTP Two-Factor Authentication (app/auth/routes.py):
  pyotp.random_base32() generates a 160-bit TOTP secret on first login.
  The secret is stored in user.totp_secret. A QR code is generated inline
  (base64-encoded PNG) for scanning with Google Authenticator or Authy.
  pyotp.TOTP.verify(token, valid_window=1) allows ±30 seconds clock skew.
  2FA state is tracked in session['2fa_verified'] — any route decorated
  with @require_2fa checks this flag.

SQL Injection Prevention (all database access):
  SQLAlchemy ORM is used exclusively — zero raw SQL queries exist in the
  codebase. All queries use Python objects and ORM methods:
    Student.query.filter_by(student_number=sn).first()
  SQLAlchemy generates parameterised queries internally, which the database
  driver executes with bound parameters — preventing any form of SQL injection.

XSS Prevention (app/utils/validators.py):
  bleach.clean(value, tags=[], strip=True) strips all HTML from every
  input field before storage. Jinja2 auto-escaping provides a second layer
  at render time, encoding <, >, &, " in all template variables. The
  Content-Security-Policy header provides a browser-side third layer.

CSRF Protection (all forms):
  Flask-WTF injects a {{ form.hidden_tag() }} hidden input containing a
  time-limited HMAC token (expires 1 hour). Any POST request without a
  valid CSRF token receives HTTP 400. SameSite=Lax cookies provide
  additional CSRF mitigation for simple cross-origin requests.

Account Lockout (app/auth/routes.py):
  After 5 consecutive failed login attempts, user.locked_until is set to
  current_time + 15 minutes. Every login attempt checks is_locked() before
  proceeding. Lockout events are recorded in the audit log.

Security Headers (app/__init__.py):
  Applied via @app.after_request to every HTTP response:
  - X-Frame-Options: SAMEORIGIN — prevents clickjacking
  - X-Content-Type-Options: nosniff — prevents MIME-type sniffing
  - X-XSS-Protection: 1; mode=block — legacy XSS filter
  - Referrer-Policy: strict-origin-when-cross-origin — prevents referrer
    leakage
  - Content-Security-Policy: restricts script/style/image sources to
    known-safe origins, preventing XSS

Role-Based Access Control (app/utils/decorators.py):
  Two decorators enforce RBAC:
  @role_required(*roles): checks current_user.role against allowed roles,
    returns HTTP 403 on failure.
  @require_2fa: checks session['2fa_verified'], redirects to 2FA page if
    absent.
  Both decorators are applied to every protected route.

JWT REST API (app/api/routes.py):
  POST /api/v1/token authenticates credentials and returns a JWT with 1-hour
  expiry. All /api/v1/* endpoints require a valid Bearer token. Object-level
  authorisation ensures teachers can only retrieve their students' data via
  the API. CSRF is exempt for API endpoints (stateless, no cookies).

7. SECURITY TESTING (SSDLC PHASE 5)
============================================================

7.1 Static Analysis (SAST)

Code review was conducted against OWASP Secure Coding Guidelines.
Key findings and remediations:

  Finding ST-01: Input fields not sanitised before storage.
  Remediation: Added sanitise_input() wrapper using bleach.clean() on all
               user-supplied strings before ORM operations.
  Status: RESOLVED

  Finding ST-02: Generic error handler leaking Flask debug info.
  Remediation: Set debug=False; added custom error handlers for 403, 404,
               429, 500 returning generic messages.
  Status: RESOLVED

  Finding ST-03: No CSRF token on state-changing forms.
  Remediation: All forms use FlaskForm with {{ form.hidden_tag() }};
               WTF_CSRF_ENABLED = True in config.
  Status: RESOLVED

  Finding ST-04: No rate limiting on login endpoint.
  Remediation: @limiter.limit("10 per minute") on /auth/login and
               /auth/verify-2fa; 5/minute on /api/v1/token.
  Status: RESOLVED

7.2 Manual Penetration Testing

SQL Injection Test:
  Attack: Submitted username "admin' OR '1'='1" in login form.
  Result: SQLAlchemy ORM treated the entire string as the literal username
          value. No SQL injection occurred. Login failed with generic error.
  Status: PASS — NOT VULNERABLE

XSS Test:
  Attack: Submitted "<script>alert('XSS')</script>" as a student name.
  Result: bleach.clean() stripped all HTML tags; stored value was
          "alert('XSS')". Jinja2 further encoded the & characters on render.
          No script executed.
  Status: PASS — NOT VULNERABLE

CSRF Test:
  Attack: Crafted a forged POST request to /teacher/students/1/delete
          without a CSRF token.
  Result: Flask-WTF rejected the request with HTTP 400 Bad Request.
          Student record was not deleted.
  Status: PASS — NOT VULNERABLE

Brute Force Test:
  Attack: Submitted 6 consecutive incorrect passwords for admin account.
  Result: After 5 failures, account was locked with a 15-minute lockout.
          6th attempt returned lockout message; no further attempts accepted.
  Status: PASS — LOCKOUT ENFORCED

IDOR Test (Insecure Direct Object Reference):
  Attack: As teacher jsmith, requested GET /teacher/students/999/edit where
          student 999 belongs to teacher mwang's course.
  Result: Server returned HTTP 403 Forbidden. Object-level RBAC check
          confirmed course membership before serving the edit form.
  Status: PASS — NOT VULNERABLE

Privilege Escalation Test:
  Attack: As student S10001, directly navigated to /admin/users.
  Result: @role_required('admin') decorator returned HTTP 403 immediately,
          before executing any view logic.
  Status: PASS — NOT VULNERABLE

Session Management Test:
  Attack: Copied session cookie from one browser and replayed in another.
  Result: Flask-Login session_protection="strong" detected IP/user-agent
          mismatch and invalidated the session.
  Status: PASS — SESSION PROTECTED

8. SECURE DEPLOYMENT (SSDLC PHASE 6)
============================================================

8.1 Production Security Configuration

The following steps must be completed before production deployment:

  1. Replace SQLite with PostgreSQL: Set SMS_DATABASE_URL environment variable
     to a PostgreSQL connection string. SQLite is single-writer and not
     suitable for concurrent production use.

  2. Set environment variables (never hard-code):
       SECRET_KEY=<64-char random hex>
       JWT_SECRET_KEY=<64-char random hex>
       ENCRYPTION_KEY=<64-char hex of 32-byte AES key>
       SESSION_COOKIE_SECURE=True   (requires HTTPS)

  3. Deploy behind HTTPS: Use nginx + Let's Encrypt, or a cloud load balancer
     with TLS termination. Enforce HSTS:
       Strict-Transport-Security: max-age=31536000; includeSubDomains

  4. Run with a production WSGI server: gunicorn or waitress — never the
     Flask development server in production.
       gunicorn -w 4 -b 127.0.0.1:8000 "run:app"

  5. Set debug=False (already configured in run.py).

  6. Remove seed.py and .encryption_key from production deployments. Store
     the encryption key in a secrets manager (AWS Secrets Manager, Azure
     Key Vault, or HashiCorp Vault).

  7. Restrict database user permissions: the application DB user should only
     have SELECT, INSERT, UPDATE, DELETE privileges — not DROP or ALTER.

8.2 Dependency Security

All dependencies are pinned to exact versions in requirements.txt to prevent
supply-chain attacks. Before deployment, run:
  pip-audit -r requirements.txt
to check for known CVEs in all pinned packages.

8.3 Incident Response

If a security breach is detected:
  1. Rotate the ENCRYPTION_KEY (re-encrypt all student records with new key).
  2. Invalidate all active sessions (clear session store).
  3. Rotate SECRET_KEY and JWT_SECRET_KEY.
  4. Review AuditLog for the relevant time window.
  5. Notify affected students per Privacy Act 2020 breach notification
     requirements (within 72 hours if high risk).
  6. Preserve logs and take a database snapshot for forensic analysis.

9. MAINTENANCE AND MONITORING (SSDLC PHASE 7)
============================================================

9.1 Security Logging

The AuditLog model records the following event types:
  LOGIN_SUCCESS / LOGIN_FAIL — all authentication attempts
  LOGIN_2FA_PENDING — pre-2FA state
  2FA_SETUP / 2FA_FAIL — 2FA configuration and verification
  ACCOUNT_LOCKED — brute-force lockout events
  LOGOUT — session termination
  PASSWORD_CHANGE / PASSWORD_CHANGE_FAIL
  STUDENT_CREATE / STUDENT_UPDATE / STUDENT_DELETE
  USER_CREATE / USER_ACTIVATE / USER_DEACTIVATE
  COURSE_CREATE

Every event records: user_id, action, resource type, resource ID, details
(no sensitive data), IP address, status, and UTC timestamp. Admins can
view paginated audit logs at /admin/audit.

9.2 Vulnerability Disclosure

A responsible disclosure process should be established:
  - Publish a security.txt file at /.well-known/security.txt
  - Designate a security contact email
  - Commit to a 90-day remediation timeline for disclosed vulnerabilities
  - Document the patch release process

9.3 Patch Management

  - Subscribe to security advisories for all dependencies (PyPI, GitHub
    Security Advisories, CVE feeds)
  - Run pip-audit weekly in CI/CD pipeline
  - Apply security patches within 7 days of disclosure
  - Re-run OWASP ZAP scan after any significant code change

9.4 Lessons Learned

  1. Security-by-default from day one is significantly less work than
     retrofitting security controls. Implementing RBAC from the first route
     required no refactoring — adding it later would have required touching
     every view function.

  2. The ORM approach (SQLAlchemy) eliminated an entire vulnerability class
     (SQL injection) structurally, without requiring developers to remember
     to sanitise inputs for database queries.

  3. AES-GCM's authentication tag provides free tamper detection — storing
     PII in GCM mode means any database-level tampering is detected
     immediately on decryption, turning an integrity threat into an
     exception rather than a silent exploit.

  4. Rate limiting and account lockout are easy to implement but are
     frequently omitted in student projects. This assessment demonstrated
     that adding both required only two decorators and two configuration
     values.

  5. The STRIDE methodology provided a structured way to identify threats
     that manual review might miss — particularly T2 (CSRF) and E2 (API
     IDOR), which are easy to overlook in initial design.

10. CONCLUSION
============================================================

SecureSMS demonstrates that the Secure Software Development Lifecycle can
be practically applied to a real-world educational application, resulting
in a system that mitigates all relevant OWASP Top 10 vulnerabilities while
remaining functional and usable. The project implemented 12 active security
controls — AES-256-GCM encryption, bcrypt hashing, TOTP 2FA, CSRF
protection, SQL injection prevention, XSS sanitisation, RBAC, rate limiting,
account lockout, security headers, JWT API authentication, and comprehensive
audit logging.

The STRIDE threat model identified 10 specific threats across all six
categories; all 10 were fully mitigated through design and implementation
controls. Security testing confirmed that the mitigations are effective
against SQL injection, XSS, CSRF, brute force, IDOR, and privilege
escalation attacks.

The most significant lesson from this project is that security-by-design
is more effective and less costly than security-by-retrofit. By defining
security requirements before writing code (Phase 1), modelling threats
before designing the architecture (Phase 2), and applying secure design
principles before implementation (Phase 3), the resulting system achieved
a stronger security posture with less rework than a traditional
development-first, security-later approach.

Future work would include replacing the SQLite database with PostgreSQL for
production, implementing HSTS and full TLS termination, integrating a CI/CD
pipeline with automated SAST (Bandit) and DAST (OWASP ZAP) scanning, and
adding email-based breach alerting.
