[TITLE]
The Problem: Student Data Is at Risk

[THREE COLUMNS]

COLUMN 1 — The Threat Landscape
• Educational institutions are frequent targets of data breaches
• University cyber attacks increased 44% in 2023 (IBM Cost of a Data Breach)
• Student PII (name, email, phone, grades) is highly sensitive
• Poorly secured systems expose thousands of records with a single SQL injection

COLUMN 2 — Common Vulnerabilities in Student Systems
• Plaintext password storage
• No multi-factor authentication
• SQL injection in search/filter fields
• No encryption of PII at rest
• No access control between teacher roles
• No audit trail for who accessed what

COLUMN 3 — Regulatory Requirements
• New Zealand Privacy Act 2020 — mandatory breach reporting
• GDPR principles (data minimisation, encryption, access control)
• ISO/IEC 27001 — Information Security Management
• NIST SP 800-53 — Security and Privacy Controls

[TITLE]
Our Solution: SecureSMS

[LARGE CALLOUT BOX]
A web application that manages student enrolment data with
SECURITY BUILT IN FROM THE GROUND UP
— not bolted on as an afterthought.

[FOUR KEY POINTS with icons]
🔒  All PII encrypted with AES-256-GCM before it reaches the database
🛡️  Two-factor authentication (TOTP) mandatory for every user
👥  Role-based access: Admin / Teacher / Student — no privilege escalation
📋  Every security event logged to an immutable audit trail

[WHAT IT DOES]
• Admins manage users, courses, and view the audit log
• Teachers add, edit, and view students enrolled in their courses only
• Students log in to view their own record — and nothing else
• A REST API provides JWT-authenticated data access for integrations

[SPEAKER NOTES]

[TITLE]
Phase 1 — Security Requirements

[LEFT COLUMN: Requirements by CIA pillar]

CONFIDENTIALITY
• SR-01: All PII (name, email, phone, grade) encrypted at rest with AES-256-GCM
• SR-02: Passwords stored as bcrypt hashes (work factor ≥ 12)
• SR-03: Session tokens must be HttpOnly, Secure, SameSite=Lax
• SR-04: Database credentials stored as environment variables only

INTEGRITY
• SR-05: CSRF tokens on all state-changing requests
• SR-06: Input sanitised with bleach before storage (XSS prevention)
• SR-07: ORM-only database access (no raw SQL)
• SR-08: Audit log entries are append-only (no UPDATE/DELETE)

AVAILABILITY
• SR-09: Rate limiting on login (10/min) and API token endpoints (5/min)
• SR-10: Account lockout after 5 failed attempts for 15 minutes
• SR-11: Session expires after 30 minutes of inactivity

AUTHENTICATION & AUTHORISATION
• SR-12: MFA required (TOTP RFC 6238) for all users
• SR-13: Role-based access: Admin, Teacher, Student — enforced server-side
• SR-14: Object-level authorisation — users may only access their own data

[RIGHT COLUMN: Standards mapped]
• OWASP Top 10 2021 — all 10 categories addressed
• NZ Privacy Act 2020 — Principle 5 (storage security)
• NIST SP 800-53 — AC (Access Control), AU (Audit), IA (Identification & Auth)
• ISO 27001 — Annex A controls A.9 (Access), A.10 (Cryptography)

[SPEAKER NOTES]
We defined requirements BEFORE writing any code. This is the key difference
between security-aware and security-ignorant development.

[TITLE]
Phase 3 & 4 — Secure Design & Implementation

[LEFT HALF: Design Principles]

DEFENCE IN DEPTH
Multiple independent controls — if one fails, another catches the attack.
Login requires: password (bcrypt) AND TOTP code AND account not locked.

LEAST PRIVILEGE
• Students see only their own record
• Teachers see only students in their assigned courses
• Admin-only routes protected with @role_required('admin')

ZERO TRUST
• Every request re-verified server-side — no client-side trust
• Session token rotated on privilege change (login, 2FA verify)
• JWT tokens for API expire after 1 hour

SECURITY BY DEFAULT
• CSRF protection on by default (Flask-WTF)
• Security headers applied to ALL responses (after_request hook)
• HttpOnly + SameSite cookies — no JavaScript can steal sessions

[RIGHT HALF: Security Headers Implemented]
Content-Security-Policy: script-src 'self' cdn.jsdelivr.net
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN (clickjacking protection)
X-XSS-Protection: 1; mode=block
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
Strict-Transport-Security: max-age=31536000 (HSTS)

[SPEAKER NOTES]
Security headers cost nothing to implement and protect against entire categories
of attack — clickjacking, MIME sniffing, protocol downgrade attacks.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[TITLE]
12 Active Security Controls in Production

[3-COLUMN GRID with icons and brief descriptions]

1. AES-256-GCM Encryption
   All PII fields (name, email, phone, grade) encrypted
   with unique 96-bit nonce per value. Authenticated encryption
   detects tampering. Even if DB is stolen, data is unreadable.

2. bcrypt Password Hashing (w=12)
   ~300ms hash time intentionally slows brute-force.
   Salted per-user — rainbow tables cannot be used.

3. TOTP Two-Factor Authentication
   RFC 6238 standard. QR code enrolment with any TOTP app.
   6-digit code valid for 30-second window. Rate-limited.

4. CSRF Token Protection
   Flask-WTF generates a unique token per form.
   Cross-Site Request Forgery is blocked on all POST endpoints.

5. SQL Injection Prevention
   SQLAlchemy ORM — zero raw SQL in the entire codebase.
   Query parameters are never string-interpolated.

6. XSS Input Sanitisation
   bleach.clean() strips all HTML tags and JS before storage.
   No user input is ever rendered as raw HTML.

7. Role-Based Access Control (RBAC)
   Three roles: Admin, Teacher, Student. @role_required decorator
   enforced server-side. HTTP 403 for unauthorised access.

8. Rate Limiting
   Login: max 10 req/min. API token: max 5 req/min.
   Flask-Limiter returns HTTP 429 Too Many Requests.

9. Account Lockout Policy
   5 failed login attempts → 15-minute lockout.
   Failed attempts reset on successful authentication.

10. Immutable Audit Logging
    Every login, 2FA event, CRUD operation recorded with
    timestamp, user ID, action, IP address, and outcome.

11. Secure Session Cookies
    HttpOnly (no JS access), SameSite=Lax (CSRF mitigation),
    30-minute lifetime. session_protection='strong'.

12. JWT REST API Authentication
    Bearer tokens for /api/v1/ endpoints. 1-hour expiry.
    Object-level authorisation enforced per request.

[SPEAKER NOTES]
All 12 controls are visible in the running application — point to the
Admin Dashboard "Active Security Controls" panel as evidence.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[TITLE]
Deep Dive: AES-256-GCM Field Encryption

[VISUAL: Encryption flow diagram]

PLAINTEXT: "Alice Johnson"
     ↓
[Generate 12-byte random nonce per field]
     ↓
[AES-256 GCM Cipher with 256-bit key from .encryption_key file]
     ↓
OUTPUT = Base64URL( nonce[12 bytes] || ciphertext || GCM_tag[16 bytes] )
     ↓
STORED IN DATABASE as: "bXlub25jZXh4eHh4eA...AQIDBAUGBwgJCg=="

[WHY GCM MODE?]
• AES-GCM provides BOTH confidentiality AND authenticity
• GCM tag detects tampering — if the encrypted value is modified, decryption FAILS
• Other modes (AES-CBC) provide confidentiality only
• 256-bit key = 2²⁵⁶ possible keys = computationally infeasible to brute-force

[WHAT FIELDS ARE ENCRYPTED?]
Field           | Stored As   | Reason
──────────────────────────────────────────────────────────────
student_number  | PLAINTEXT   | Used as JOIN key — must be searchable
name_enc        | ENCRYPTED   | PII — Privacy Act Principle 5
email_enc       | ENCRYPTED   | PII — Identity information
phone_enc       | ENCRYPTED   | PII — Contact information
grade_enc       | ENCRYPTED   | Academic PII — sensitive

[SPEAKER NOTES]
The student_number is intentionally left unencrypted because it is used as
a search key. All human-identifiable PII is encrypted. If the database file
is stolen, the attacker sees only random-looking base64 strings.

Data Flow: How Student PII Is Protected

[ANNOTATED FLOW DIAGRAM — describe for slide builder]

WRITE FLOW (Adding a student):
Browser Form
  → [CSRF token validated by Flask-WTF]
  → [bleach.clean() strips HTML/JS from all text fields]
  → [validate_password_strength() / validate_student_number()]
  → [encrypt_field(name, key) → AES-256-GCM ciphertext]
  → [encrypt_field(email, key) → AES-256-GCM ciphertext]
  → [encrypt_field(phone, key) → AES-256-GCM ciphertext]
  → [encrypt_field(grade, key) → AES-256-GCM ciphertext]
  → SQLAlchemy INSERT (parameterised — no SQL injection possible)
  → Database (all PII columns are unreadable ciphertext)
  → AuditLog entry written (STUDENT_CREATED, user_id, ip, timestamp)

READ FLOW (Viewing students list):
Teacher navigates to /teacher/students
  → [@login_required → session token validated]
  → [@role_required('teacher','admin') → role checked server-side]
  → [@require_2fa → session['2fa_verified'] checked]
  → SQLAlchemy SELECT (teacher sees only their enrolled students)
  → [decrypt_field(name_enc, key) → "Alice Johnson"]
  → [decrypt_field(email_enc, key) → "alice@student.edu"]
  → Template renders decrypted values
  → AuditLog: STUDENT_VIEW event recorded

[SPEAKER NOTES]
This shows that security is applied at every layer of the stack — not just
at the boundary. Even if someone bypasses authentication, the DB data is
still encrypted and unreadable without the key.

[TITLE]
Lessons Learned

[FOUR QUADRANT LAYOUT]

QUADRANT 1: What Worked Well ✅
• Starting with threat modelling focused implementation on real risks
• ORM choice (SQLAlchemy) eliminated SQL injection by design — no extra effort
• AES-256-GCM encryption at the application layer is transparent to the ORM
• Blueprint architecture made RBAC clean and maintainable
• Environment variables for secrets prevented accidental credential commits

QUADRANT 2: Challenges Encountered ⚠️
• Content Security Policy tuning — inline scripts had to be externalised
• Bootstrap CDN integrity hash mismatches caused silent load failures
• System env var conflicts (DATABASE_URL) required custom variable naming
• TOTP clock drift can cause 2FA failures — server time sync is critical

QUADRANT 3: Security Trade-offs Considered 🔄
• AES encryption makes student PII non-searchable (design decision: search by student number only)
• bcrypt work factor 12 adds ~300ms to login — acceptable latency for security gain
• Session timeout of 30 min may frustrate long-working teachers — configurable

QUADRANT 4: What We Would Do Differently in Production 🚀
• Use Redis for rate-limiter storage (prevents bypass on multi-instance deployment)
• Implement PostgreSQL with encrypted connection string
• Add automated dependency scanning (GitHub Dependabot / Snyk)
• Implement email alerts for lockout and unusual access patterns
• Add WebAuthn/FIDO2 as stronger 2FA alternative to TOTP

[SPEAKER NOTES]
Be honest about challenges — examiners appreciate critical reflection.
Show that the team understands production-grade security considerations.

[ANTICIPATED QUESTIONS — for speakers to prepare]

Q: Why AES-256-GCM instead of AES-256-CBC?
A: GCM provides authenticated encryption — it simultaneously encrypts AND
   creates a cryptographic tag that detects tampering. CBC provides
   confidentiality only. GCM is the current industry standard for field encryption.

Q: Isn't storing the encryption key in a file insecure?
A: For this prototype, yes — in production the key would be stored in a
   Hardware Security Module (HSM) or secrets manager (e.g. AWS Secrets Manager,
   HashiCorp Vault). The file-based approach demonstrates the concept correctly.

Q: Why SQLite and not PostgreSQL?
A: SQLite is used for the development prototype to keep setup simple for
   assessment demonstration. The application is configured to switch to
   PostgreSQL by setting the SMS_DATABASE_URL environment variable.
   All SQL is generated by SQLAlchemy ORM and is database-agnostic.

Q: How does the TOTP work if the server clock drifts?
A: pyotp accepts codes from the previous and next 30-second window (±1 step)
   to handle minor clock differences. For production, NTP time synchronisation
   is documented in the deployment guide.

Q: Could an attacker exfiltrate the database and decrypt it?
A: Only if they also obtained the encryption key from a separate file/environment.
   This is why defence in depth matters — the attacker needs to breach the
   server AND extract the key. Without the key, all PII is random-looking bytes.

COMMON EXAMINER QUESTIONS — SHORT ANSWERS
• "Why not bcrypt work factor 14?"
  → 12 gives ~300ms hash time which prevents brute-force. Factor 14 = ~1.2s per attempt
    which creates poor UX for legitimate users without significant security gain against
    dictionary attacks (the main threat).

• "How is the audit log protected from deletion by an admin?"
  → In this prototype, admins can delete via the ORM. In production, audit logs
    would be written to a separate WORM (Write Once Read Many) storage system
    or a centralised SIEM to prevent tampering.

• "Why use Flask and not Django?"
  → Flask's micro-framework nature allowed us to choose each security library
    individually, demonstrating understanding of each control. Django's
    ORM and auth are built-in; Flask requires explicit security choices,
    which better demonstrates security-conscious development.
